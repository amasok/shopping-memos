# Product Requirements Document (PRD) - 買い物メモアプリ

## 1. 概要

### 1.1 プロダクトビジョン
家族やグループで共有できる買い物メモアプリ。「買いたいもの」を日常的にストックしておき、買い物時にタグベースで効率的にリストを作成・消化できる。

**個人でもグループでも使いやすい設計**を重視する。

### 1.2 背景・課題
- 買い物メモが家族間で共有されず、同じものを買ってしまう
- 紙のメモは忘れやすく、更新が面倒
- 店舗ごとに買うものが違うが、既存アプリでは対応しにくい

### 1.3 解決策
- グループ単位でアイテムを共有（個人利用も可能）
- タグで分類し、店舗や用途に応じたリストを瞬時に作成
- 「カゴに入れた」→「購入済み」の2段階管理で買い忘れを防止

---

## 2. ターゲットユーザー

### 2.1 プライマリユーザー
| ペルソナ | 説明 |
|---------|------|
| 共働き夫婦 | 帰宅途中にスーパーに寄ることが多い。相手が何を買ったか把握したい |
| 子育て世帯 | 日用品の消耗が早く、「なくなりそう」を気づいた時にメモしたい |

### 2.2 セカンダリユーザー
| ペルソナ | 説明 |
|---------|------|
| 一人暮らし | 個人用メモとして利用。グループ機能なしでもシンプルに使える |
| シェアハウス | 共有消耗品の管理 |

### 2.3 設計方針: 個人利用のしやすさ
- グループ未作成でも全機能が使える
- 初回ログイン時にグループ作成を強制しない
- 「個人の買いたいもの」と「グループ共有」を明確に分離

### 2.4 ユースケース
1. **日常**: 冷蔵庫を開けて「牛乳がない」→ アプリで即登録
2. **買い物前**: 「スーパーA」タグでリスト作成 → 今日買うものを確認
3. **買い物中**: カゴに入れたらチェック → 買い忘れ防止
4. **買い物後**: 購入完了 → 履歴に記録、買わなかったものは残る
5. **共有**: 妻がアイテム追加 → 夫が帰宅途中に確認して購入

## 6. データモデル概要

### 6.1 エンティティ関連図（ER図）

```
User ─┬─< UserGroup >─┬─ Group ─< InviteLink
      │               │
      │               ├─< ShoppingItem >─┬─< ItemTag >─┬─ Tag
      │               │                  │             │
      │               └─< ShoppingList >─┴─< ListItem >┘
      │
      └─< PurchaseHistory
```

### 6.2 主要エンティティ

| エンティティ | 説明 |
|-------------|------|
| User | ユーザー情報（Google OAuth から取得） |
| Group | 共有グループ |
| UserGroup | ユーザーとグループの中間テーブル（役割: owner/member） |
| InviteLink | 招待リンク（トークン、有効期限7日間、1回使用で無効化） |
| ShoppingItem | 買いたいもの（グループ紐付けは任意） |
| Tag | タグ（グループ紐付けは任意） |
| ItemTag | アイテムとタグの中間テーブル |
| ShoppingList | 買い物リスト |
| ListItem | リストに含まれるアイテム（状態: pending/in_cart/purchased） |
| PurchaseHistory | 購入履歴 |

### 6.3 データモデルの設計方針

#### アイテムとグループの関係
- **1アイテム = 1グループ（または個人）**: アイテムは複数グループに所属しない
- グループに紐付けない場合は「個人のアイテム」として扱う

#### アイテムとリストの関係
- **1アイテムは複数のリストに登場しうる**（時系列的に）
- 例: 「牛乳」を西友で買おうとしたが売り切れ → 「買いたいもの」に戻る → 別の日にイオンのリストに再登場
- ListItem はその時点のスナップショットとして、アイテム名・数量を保持する（後からアイテムが編集されても履歴には影響しない）

#### 招待リンク
- 有効期限: **7日間**
- 1回使用で無効化（再利用不可）
- 同じグループに複数の招待リンクを発行可能

#### ローカルストレージとサーバー同期

**ゲストモード（未ログイン）時:**
- データは IndexedDB に保存
- ローカルIDはUUID形式で生成（サーバーIDと区別可能）
- オフラインでも全機能が動作

**ログイン時のマージ戦略:**
1. ローカルデータをサーバーにアップロード
2. ローカルIDをサーバーIDに置き換え
3. マージ完了後、ローカルデータをクリア（サーバーが正となる）
4. 以降はサーバーのデータを使用

**競合解決（同じユーザーが別デバイスで既にログイン済みの場合）:**
- ローカルデータを「追加」としてマージ（既存データは上書きしない）
- 重複アイテムはユーザーが手動で整理

```
└── infrastructure/         # インフラ層
    ├── db/                # Drizzle スキーマ、マイグレーション
    └── repositories/      # リポジトリ実装
```

#### CQRS（コマンドクエリ責務分離）

| 責務 | 説明 |
|------|------|
| Command（書き込み） | ドメインロジックを経由、エンティティを操作 |
| Query（読み取り） | Drizzle で直接SQL組み立て、DTO を返す |

**Drizzle ORM を選択した理由:**
- SQL組み立て型でCQRSのQuery側に適している
- 型安全なクエリビルダー
- ActiveRecord的な「お作法」に縛られない
- 複雑なJOINや集計もSQLライクに書ける

### 10.3 ファネル分析

#### ファネル1: 買い物フロー
```
item_add → list_create → list_start → item_check → purchase_complete
```
**見たいこと**: どこで離脱しているか、リスト作成後に実際に買い物に行く割合

#### ファネル2: ログイン転換
```
first_visit → item_add（3回以上） → login_prompt_show → login_start → login_complete
```
**見たいこと**: ゲストからログインへの転換率、どの促進UIが効果的か

#### ファネル3: グループ機能利用
```
login_complete → group_create → invite_create → invite_accept
```
**見たいこと**: ログインユーザーのグループ作成率、招待の成功率

### 10.4 主要KPI（GA4で計測）

| 指標 | 定義 | 目標 |
|------|------|------|
| DAU/WAU/MAU | アクティブユーザー数 | - |
| リスト完了率 | purchase_complete / list_create | 70%以上 |
| ログイン転換率 | login_complete / first_visit | 20%以上 |
| グループ作成率 | group_create / login_complete | 30%以上 |
| 招待成功率 | invite_accept / invite_create | 50%以上 |

### 10.5 実装方針
- MVP: 基本イベント + 主要カスタムイベント（item_add, list_create, purchase_complete, login系）
- Phase 2: 全カスタムイベント + ファネル分析の本格運用
