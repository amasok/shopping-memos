## Requirements

### Requirement: メールアドレスとワンタイムコードでのログイン

システムは、メールアドレスに 6 桁の数字のワンタイムコードを送り、そのコードを入力するとログインできるようにしなければならない（MUST）。登録されていないアドレスなら、コードの照合に成功した時点で、表示名が空のユーザーを作ってログインさせる。Google でのログインは提供しない。ログインした後は、ゲストのデータの取り込み（今の `DataMergeContext`）が今と同じく動き、ログインの前にいた画面（なければホーム）に移る。戻り先は、アプリと同じオリジンに解決されるパスだけを受け付ける。

#### Scenario: 届いたコードを入力するとログインできる
- **WHEN** 登録済みのアドレスを入力してコードを送り、届いた 6 桁のコードを入力する
- **THEN** そのアドレスのユーザーとしてログインし、ホームに移る

#### Scenario: 未登録のアドレスはコードの照合でユーザーが作られる
- **WHEN** 未登録のアドレスでコードを送り、届いたコードを入力する
- **THEN** そのアドレスで表示名が空のユーザーが 1 件作られ、そのユーザーとしてログインする

#### Scenario: コードを送っただけではユーザーは作られない
- **WHEN** 未登録のアドレスでコードを送り、コードを入力しない
- **THEN** ユーザーは作られない

#### Scenario: ログインするとゲストのデータが取り込まれる
- **WHEN** ゲストで商品を作ってから、コードでログインする
- **THEN** その商品がログインしたユーザーのデータとして見える

#### Scenario: ログインの前にいた画面に戻る
- **WHEN** グループの画面からログイン画面に移り、コードでログインする
- **THEN** グループの画面に戻る

#### Scenario: 戻り先に別のサイトは指定できない
- **WHEN** 戻り先に `https://evil.example/`・`//evil.example/`・`/\evil.example`・タブや改行を含む `/\t/evil.example` のどれかを指定してログイン画面を開き、コードでログインする
- **THEN** ホームに移り、別のサイトには移らない

#### Scenario: ログイン画面に Google のボタンがない
- **WHEN** ログイン画面を開く
- **THEN** Google でログインするボタンはなく、メールアドレスの入力欄と「コードを送信」がある

#### Scenario: オフラインではコードを送れない
- **WHEN** オフラインの状態でログイン画面を開く
- **THEN** 「オフラインのためログインできません」が出て、「コードを送信」と「ログイン」は押せない

### Requirement: 使わない認証の API を閉じる

システムは、認証の API（`/api/auth/*`）のうち、コードの送信（種類がログインのものだけ）・コードでのログイン・セッションの取得・ログアウトだけを受け付け、それ以外のパス（パスワードでの登録・ログイン、ソーシャルログイン、メールの確認、パスワードの再設定、コードの確認だけをする API など）には 404 を返さなければならない（MUST）。受け付けるパスは許可リストで決め、ライブラリが新しいパスを足しても自動では開かない。後の変更（表示名・すべての端末からログアウト・パスキー）は、その変更で許可リストに足す。

#### Scenario: 許可していないパスは 404 になる
- **WHEN** `/api/auth/sign-up/email`・`/api/auth/sign-in/email`・`/api/auth/sign-in/social`・`/api/auth/email-otp/check-verification-otp`・`/api/auth/email-otp/verify-email`・`/api/auth/forget-password/email-otp`・`/api/auth/email-otp/reset-password` のそれぞれに POST する
- **THEN** どれも 404 が返り、メールは送られず、ユーザーもセッションも作られない

#### Scenario: ログイン以外の種類のコードの送信は断る
- **WHEN** コードの送信に、種類としてメールの確認やパスワードの再設定を指定する
- **THEN** 送信は断られ、メールは送られない

#### Scenario: 許可したパスは動く
- **WHEN** コードの送信・コードでのログイン・セッションの取得・ログアウトを、アプリの画面から順に呼ぶ
- **THEN** どれも処理される

### Requirement: メールアドレスの正規化

システムは、コードの送信・照合・ユーザーの作成の前に、メールアドレスを Unicode 正規化（NFKC）し、前後の空白を除き、小文字にしてから形式を確かめなければならない（MUST）。正規化の後に ASCII 以外の文字が残るアドレスは受け付けない。ユーザーは正規化した後のアドレスで一意にする。

#### Scenario: 大文字や前後の空白があっても同じユーザーになる
- **WHEN** `Taro@Example.com ` でコードを送ってログインし、後で `taro@example.com` でログインする
- **THEN** 2 回とも同じユーザーとしてログインする

#### Scenario: 全角の英数字は正規化して受け付ける
- **WHEN** `ｔａｒｏ＠ｅｘａｍｐｌｅ．ｃｏｍ` でコードを送ってログインする
- **THEN** `taro@example.com` のユーザーとしてログインする

#### Scenario: 正規化の後も ASCII 以外が残るアドレスは受け付けない
- **WHEN** キリル文字のホモグリフ（例: ラテン文字の a に見える `а`）や漢字を含むアドレスでコードを送る
- **THEN** 送信は形式のエラーになり、メールは送られない

### Requirement: コードの有効期限・試行回数・使い回しの禁止

システムは、コードを 5 分で失効させ、1 つのコードの照合を 3 回までにし、照合に成功したコードと、新しいコードを送った後の古いコードを使えなくしなければならない（MUST）。照合の回数は、同時に照合を送っても 3 回を超えてはならない（MUST NOT）。DB にはコードのハッシュだけを持ち、平文のコードを残してはならない（MUST NOT）。

#### Scenario: 5 分を過ぎたコードではログインできない
- **WHEN** コードを送ってから 5 分を過ぎた後に、そのコードを入力する
- **THEN** ログインできず、「コードの有効期限が切れました。再送信してください」が出る

#### Scenario: 3 回まちがえるとコードが無効になる
- **WHEN** まちがったコードを 3 回入力した後に、正しいコードを入力する
- **THEN** ログインできず、「コードの有効期限が切れました。再送信してください」が出る

#### Scenario: 同時に照合を送っても 3 回までしか照合されない
- **WHEN** 1 つのコードに、まちがったコードの照合を同時に 10 件送り、その後に正しいコードを入力する
- **THEN** 照合として扱われるのは 3 件までで、残りは期限切れと同じ扱いになり、正しいコードでもログインできない

#### Scenario: まちがったコードには不一致の文言を出す
- **WHEN** まちがったコードを 1 回入力する
- **THEN** 「コードが正しくありません」が出て、もう一度入力できる

#### Scenario: 再送するとコードを送り直してログインできる
- **WHEN** 3 回まちがえて無効になった後に、60 秒以上たってから再送し、新しいコードを入力する
- **THEN** ログインできる

#### Scenario: 使ったコードではもう一度ログインできない
- **WHEN** コードでログインし、ログアウトしてから同じコードを入力する
- **THEN** ログインできない

#### Scenario: 新しいコードを送ると古いコードは使えない
- **WHEN** コードを送り、60 秒以上たってからもう一度送り、1 通目のコードを入力する
- **THEN** ログインできない

#### Scenario: DB には平文のコードが残らない
- **WHEN** コードを送る
- **THEN** 認証の検証用のテーブルに、送ったコードと同じ文字列の値はない

### Requirement: 再送の間隔

システムは、同じメールアドレスへのコードの送信を 60 秒に 1 回までにしなければならない（MUST）。ログイン画面の「再送信」は、送信から 60 秒たつまで押せない。

#### Scenario: 送信から 60 秒は再送できない
- **WHEN** コードを送った直後に、コードの入力の画面を見る
- **THEN** 「再送信」は押せず、60 秒たつと押せるようになる

#### Scenario: 60 秒以内に同じアドレスに送っても 2 通目は送られない
- **WHEN** API で同じアドレスに 60 秒以内に 2 回送信する
- **THEN** メールは 1 通だけ送られ、1 通目のコードでログインできる

### Requirement: 黙って送らないときは今のコードを変えない

システムは、アドレスに結びついた理由（再送の間隔・「アドレス × IP」の上限・ロック・許可リスト外）で送信を見送るとき、新しいコードを作らず、そのアドレスの今のコードも無効にしてはならない（MUST NOT）。

#### Scenario: 上限で見送った送信では本人の手元のコードが使える
- **WHEN** 本人がコードを受け取った後に、攻撃者が別の IP から 60 秒以内に同じアドレスへ送信する
- **THEN** メールは送られず、本人の手元のコードでログインできる

### Requirement: 送信の結果でアドレスの存在が分からない

システムは、コードの送信の応答（ステータスと本文）を、アドレスが登録済みか未登録かで変えてはならない（MUST NOT）。アドレスに結びついた理由（再送の間隔・「アドレス × IP」の上限・ロック・許可リスト外）で送信を見送るときも、送ったときと同じ応答を返す。アドレスに依存しない理由（IP ごとの上限・Turnstile の失敗）では、その旨の文言を出してよい。エラーの文言に「未登録」などの登録の有無が分かる言葉を出さない。

#### Scenario: 登録済みと未登録で応答が同じ
- **WHEN** 登録済みのアドレスと未登録のアドレスで、それぞれコードを送る
- **THEN** 2 つの応答のステータスと本文は同じ

#### Scenario: アドレスの上限やロックで見送っても応答が同じ
- **WHEN** 「アドレス × IP」の上限に達したアドレスと、ロック中のアドレスで、それぞれコードを送る
- **THEN** 応答のステータスと本文は、上限に達していないアドレスに送ったときと同じで、メールは送られない

### Requirement: ボット対策

システムは、コードの送信のたびに Cloudflare Turnstile のトークンをサーバーで確かめ（siteverify）、確かめられなければ送ってはならない（MUST NOT）。確かめるときは、トークンの hostname がアプリのホストであること、action がコードの送信であることも見る。通常は操作の要らない非表示のウィジェットを使う。Preview と E2E では、Cloudflare のテスト用のキー（常に成功する）を使う。

#### Scenario: Turnstile の確認に失敗したら送らない
- **WHEN** Turnstile のトークンがない、または siteverify が失敗するリクエストでコードを送る
- **THEN** メールは送られない

#### Scenario: 別のホストや別の action のトークンでは送らない
- **WHEN** siteverify の結果の hostname がアプリのホストと違う、または action がコードの送信ではないトークンでコードを送る
- **THEN** メールは送られない

#### Scenario: Turnstile の確認に成功したら送る
- **WHEN** 有効な Turnstile のトークンを付けてコードを送る
- **THEN** メールが送られる

### Requirement: IP ごとの上限

システムは、コードの送信を IP アドレスごとに 1 分 3 通・24 時間 20 通まで、コードでのログイン（照合）を IP アドレスごとに 1 分 10 回までにしなければならない（MUST）。IP アドレスは Vercel が設定するヘッダからだけ取り、クライアントが付けた `x-forwarded-for` は使わない。IPv6 は /64 のまとまりを 1 つの IP として数える。上限は複数のサーバーのインスタンスで共有する（DB に持つ）。上限を超えたときの画面の文言は「しばらく時間をおいてからお試しください」にする。

#### Scenario: 同じ IP から 1 分に 4 通目は送られない
- **WHEN** 同じ IP から、別々のアドレスへ 1 分の間に 4 回送信する
- **THEN** 4 回目のメールは送られず、「しばらく時間をおいてからお試しください」が出る

#### Scenario: 同じ IP から 24 時間に 21 通目は送られない
- **WHEN** 同じ IP から、別々のアドレスへ 1 分 3 通以下の間隔で、24 時間に 21 回送信する
- **THEN** 21 回目のメールは送られない

#### Scenario: 同じ IP から 1 分に 11 回目の照合は断る
- **WHEN** 同じ IP から、別々のアドレスのコードの照合を 1 分の間に 11 回送る
- **THEN** 11 回目は照合されずに断られる

#### Scenario: x-forwarded-for を変えても上限は変わらない
- **WHEN** 同じ IP から、`x-forwarded-for` を毎回変えて 1 分の間に 4 回送信する
- **THEN** 4 回目のメールは送られない

#### Scenario: 同じ /64 の IPv6 は 1 つの IP として数える
- **WHEN** 同じ /64 に入る別々の IPv6 アドレスから、1 分の間に 4 回送信する
- **THEN** 4 回目のメールは送られない

### Requirement: 「アドレス × IP」ごとの上限と累積ロック

システムは、同じ「アドレス × IP」からのコードの送信を 24 時間に 5 通までにし、同じ「アドレス × IP」での照合（成功を除く）が直近 24 時間に 10 回に達したら、10 回目から 24 時間、その「アドレス × IP」からのコードでのログインを止めなければならない（MUST）。照合の回数は、同時に照合を送っても数えもれがあってはならない（MUST NOT）。コードを送り直しても照合の回数は戻さない。別の IP からの同じアドレスの送信とログインは止めない。記録のアドレスは、鍵付きのハッシュ（HMAC-SHA256）で持ち、記録は 30 日で消す。

#### Scenario: 同じアドレス × IP の 6 通目は送られない
- **WHEN** 同じ IP から同じアドレスに、60 秒以上あけて 24 時間に 6 回送信する
- **THEN** 6 回目のメールは送られない

#### Scenario: 別の IP からは同じアドレスに送れる
- **WHEN** ある IP から同じアドレスに 5 通送った後に、別の IP からそのアドレスに送信する
- **THEN** メールが送られる

#### Scenario: 失敗が 10 回に達するとその IP からはログインできない
- **WHEN** 同じ IP からコードの送り直しをはさみつつ、照合に合計 10 回失敗した後に、同じ IP から新しく送った正しいコードを入力する
- **THEN** ログインできない

#### Scenario: 同時に照合を送っても 10 回でロックされる
- **WHEN** 同じ「アドレス × IP」で照合に 9 回失敗した後に、新しく送ったコードに、まちがった照合を同時に 3 件送る
- **THEN** 照合として扱われるのは 1 件だけで、その「アドレス × IP」はロックされる

#### Scenario: ロック中でも別の IP からはログインできる
- **WHEN** ある「アドレス × IP」がロックされた後に、別の IP から同じアドレスでコードを送って入力する
- **THEN** ログインできる

#### Scenario: 記録にはアドレスの平文が残らない
- **WHEN** コードを送る
- **THEN** 送信の記録に、アドレスの平文はない

#### Scenario: 30 日より古い記録は消える
- **WHEN** 30 日より古い送信の記録がある状態で、コードを送る
- **THEN** 30 日より古い記録は消え、24 時間以内の記録は残る

### Requirement: Preview の送信先の許可リスト

システムは、`EMAIL_RECIPIENT_ALLOWLIST` が設定されているとき、そのリストにないアドレスへメールを送ってはならない（MUST NOT）。応答は送ったときと同じにする。設定されていなければ（本番）送信先を限らない。

#### Scenario: 許可リストにないアドレスには送らない
- **WHEN** 許可リストが設定された環境で、リストにないアドレスにコードを送る
- **THEN** メールは送られず、応答はリストにあるアドレスのときと同じ

#### Scenario: 許可リストが未設定なら送信先を限らない
- **WHEN** 許可リストが設定されていない環境で、任意のアドレスにコードを送る
- **THEN** メールが送られる

### Requirement: 既存の Google ユーザーの紐付け

システムは、Google でのログインで作られたユーザーのメールアドレスでコードのログインをしたとき、そのユーザー（同じ `users.id`）としてログインさせなければならない（MUST）。グループ・商品・リスト・履歴はそのまま見え、表示名は変えない。

#### Scenario: Gmail のアドレスでログインすると前のデータが見える
- **WHEN** Google のログインで作られた想定のユーザー（表示名・Gmail のアドレスあり）とそのグループ・商品がある状態で、同じアドレスでコードのログインをする
- **THEN** 同じ `users.id` のユーザーとしてログインし、そのグループと商品が見え、表示名は変わらない

#### Scenario: ログイン画面に移行の案内が出る
- **WHEN** ログイン画面を開く
- **THEN** 「ログイン方法が変わりました。以前 Google で使っていた Gmail のアドレスを入力してください」が出る

### Requirement: セッション

システムは、ログインのセッションを DB に持ち、30 日で失効させ、使っている間は 1 日ごとに期限を延ばさなければならない（MUST）。セッションの Cookie は `Secure`（ローカルの http を除く）・`HttpOnly`・`SameSite=Lax` にする。リクエストのたびに DB のセッションを確かめ、DB から消えたセッションはすぐ使えなくする。切り替えの前の Auth.js のセッション（Cookie）は受け付けない。セッションがないリクエストでは、保護された tRPC の手続きは UNAUTHORIZED（401）を返す。

#### Scenario: セッションがないと保護された API は 401 になる
- **WHEN** ログインしていない状態で、保護された tRPC の手続きを呼ぶ
- **THEN** UNAUTHORIZED が返る

#### Scenario: ログインすると tRPC でそのユーザーとして扱われる
- **WHEN** コードでログインした後に、保護された tRPC の手続きを呼ぶ
- **THEN** ログインしたユーザーの ID で処理される

#### Scenario: セッションの Cookie の属性
- **WHEN** 本番と同じ https の設定でコードでログインする
- **THEN** セッションの Cookie は `Secure`・`HttpOnly`・`SameSite=Lax` が付いている

#### Scenario: 切り替え前の Auth.js の Cookie ではログインしていない扱いになる
- **WHEN** Auth.js のセッションの Cookie だけを持ったリクエストで、保護された tRPC の手続きを呼ぶ
- **THEN** UNAUTHORIZED が返る

### Requirement: ログアウト

システムは、ログアウトすると、その端末のセッションを DB から消してすぐ無効にし、ログイン中だけの状態（merge 済みの印・選んでいたグループ）を消してゲストに戻さなければならない（MUST）。

#### Scenario: ログアウトするとゲストに戻り、保護されたデータが見えない
- **WHEN** ログインしてからログアウトする
- **THEN** ゲストの表示に戻り、ログイン中のユーザーのデータは見えない

#### Scenario: ログアウトした後は控えておいた Cookie も使えない
- **WHEN** ログアウトする前に控えておいたセッションの Cookie を、ログアウトの直後に付けて保護された tRPC の手続きを呼ぶ
- **THEN** UNAUTHORIZED が返る

### Requirement: 別のオリジンからの変更を断る

システムは、tRPC の mutation と認証の API（`/api/auth/*`）の POST で、`Origin` がアプリのオリジンと違う（`Origin: null` を含む）、または `Sec-Fetch-Site` が `cross-site` のとき、Cookie の有無にかかわらず処理せずに 403 を返さなければならない（MUST）。信頼するオリジンは本番の URL（と、環境変数で足す Preview の URL）だけにする。

#### Scenario: 別のオリジンからの mutation は 403 になる
- **WHEN** `Origin` が別のサイトのリクエストで、ログイン中のセッションの Cookie を付けて tRPC の mutation を呼ぶ
- **THEN** 403 が返り、データは変わらない

#### Scenario: 別のオリジンからのログインは 403 になる
- **WHEN** Cookie のない状態で、`Origin` が別のサイトのリクエストでコードでのログイン（照合）を POST する
- **THEN** 403 が返り、セッションの Cookie は付かない

#### Scenario: Origin が null のリクエストは 403 になる
- **WHEN** `Origin: null` で tRPC の mutation と、コードでのログインを POST する
- **THEN** どちらも 403 が返る

#### Scenario: 同じオリジンからの mutation は処理される
- **WHEN** アプリの画面から tRPC の mutation を呼ぶ
- **THEN** 処理される

### Requirement: E2E 用のログインの守り

システムは、E2E のためにコードを読み出すテスト用のルートと、コードをメールで送らずに手元に持つ仕組みを、`E2E_BUILD=true` でビルドしたときだけ含め、実行時も `E2E_TEST` が `"true"`・Vercel の環境ではない・（ルートでは）`x-e2e-token` が `E2E_SEED_TOKEN` と一致する、のすべてを満たすときだけ有効にし、テスト用のルートはそれ以外で 404 を返さなければならない（MUST）。`NODE_ENV` では判断しない。メールアドレスだけでログインできる E2E 用の Credentials は提供しない。

#### Scenario: 条件がそろうとテスト用のルートが直近のコードを返す
- **WHEN** E2E のビルドと実行時の条件がそろった状態で、テスト用のルートにアドレスとトークンを付けて問い合わせる
- **THEN** そのアドレスに直近に送ったコードが返る

#### Scenario: 条件が 1 つでも欠けるとテスト用のルートは 404 になる
- **WHEN** `E2E_TEST` がない、`VERCEL_ENV` が production か preview、トークンがない・違う、のどれかの状態でテスト用のルートに問い合わせる
- **THEN** 404 が返る

#### Scenario: 本番のビルドの NODE_ENV でも条件がそろえばテスト用のルートが動く
- **WHEN** `E2E_BUILD=true` で本番のビルドをし、`NODE_ENV=production` で動かして条件をそろえる
- **THEN** テスト用のルートが直近のコードを返す

#### Scenario: E2E_BUILD なしのビルドではコードを手元に持たない
- **WHEN** `E2E_BUILD` を付けずにビルドし、実行時に `E2E_TEST=true` を設定する
- **THEN** テスト用のルートはビルドに含まれず、コードの送信は通常の送り方（Resend、ローカルではコンソール）になる

#### Scenario: メールアドレスだけではログインできない
- **WHEN** E2E の条件がそろった状態で、コードなしにメールアドレスだけでログインしようとする
- **THEN** ログインできない
