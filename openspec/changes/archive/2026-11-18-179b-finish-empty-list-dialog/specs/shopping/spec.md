## REMOVED Requirements

### Requirement: 買い物の完了
**Reason**: チェック 0 件の完了を断り（「チェック 0 件の完了」）、カタログの照合を未購入の商品に限るため、「チェック 0 件でも完了できる」「同じ名前の購入済みの商品も購入日時を更新する」の Scenario を残せない。OpenSpec の MODIFIED は Scenario を落とせないので、名前を変えて足し直す
**Migration**: 「チェック済みの商品がある買い物の完了」と「チェック 0 件の完了」に分ける。ほかの Scenario（未チェックの商品を外す・場所・完了済み・使えないリスト・同期の conflict / rejected / LWW）はそのまま移す

### Requirement: 端末の DB の買い物の完了
**Reason**: ローカルファーストの完了を、サーバーと同じく、照合を未購入の商品に限り、チェック 0 件はエラーにするため（3 つのモードで同じ振る舞いにする。確認事項 5・6）。「同じ名前の購入済みの商品も更新する」「チェック 0 件でも完了できる」の Scenario を残せないので、名前を変えて足し直す
**Migration**: 「ローカルファーストの買い物の完了」に移す。ほかの Scenario（複合操作を 1 つ積む・完了済みはエラー）はそのまま移す

## ADDED Requirements

### Requirement: チェック済みの商品がある買い物の完了

チェック済みの商品が 1 件以上ある進行中のリストをサーバーで完了すると、システムは、チェック済みの商品と同じ名前・同じスコープの未購入のカタログの商品を購入済みにし（購入日時を完了の時刻にする）、未チェックの商品をリストから外し、リストを完了にしなければならない（MUST）。完了したリストは、購入日時が入り、購入履歴に表示される。リストから外した商品のカタログの商品は変えない（「買いたいもの」の一覧に戻る）。

#### Scenario: チェック済みの商品と同じ名前の商品を購入済みにする
- **WHEN** 「牛乳」をチェックし「卵」をチェックせずに、リストを完了する
- **THEN** 同じスコープの未購入の「牛乳」のカタログの商品に、完了の時刻が購入日時として入る
- **AND** 「卵」のカタログの商品は変わらない

#### Scenario: 同じ名前の購入済みの商品の購入日時は変えない
- **WHEN** 同じスコープに、未購入の「牛乳」と、前に購入済みになった「牛乳」があり、「牛乳」をチェックしてリストを完了する
- **THEN** 未購入の「牛乳」だけが購入済みになり、前に購入済みの「牛乳」の購入日時は変わらない

#### Scenario: 未チェックの商品をリストから外す
- **WHEN** 「卵」をチェックせずにリストを完了する
- **THEN** 完了したリスト（購入履歴）に「卵」は残らず、チェック済みの商品だけが残る
- **AND** 「卵」のカタログの商品は「買いたいもの」の一覧に出る

#### Scenario: 全部チェック済みならリストの商品はすべて残る
- **WHEN** リストの商品をすべてチェックして完了する
- **THEN** 完了したリスト（購入履歴）に、すべての商品が残る

#### Scenario: 完了したリストに購入日時と場所が入る
- **WHEN** 場所を指定してリストを完了する
- **THEN** リストの状態は完了になり、完了日時と購入日時に完了の時刻が、場所に指定した値が入る

#### Scenario: 完了済みのリストは完了できない
- **WHEN** 完了済みのリストを tRPC で完了しようとする
- **THEN** BAD_REQUEST になり、リストとカタログの商品は変わらない

#### Scenario: 使えないリストや削除したリストは tRPC で完了できない
- **WHEN** ほかのユーザーの個人のリスト・自分が入っていないグループのリスト・論理削除したリストを tRPC で完了しようとする
- **THEN** FORBIDDEN になり、リストとカタログの商品は変わらない

#### Scenario: 確認の後に使えなくなったリストは完了しない
- **WHEN** tRPC の完了で、アクセスの確認の後、書き込みの前に、リストが論理削除されるかグループから外れる
- **THEN** リストとカタログの商品は変わらず、BAD_REQUEST（「リストが見つかりません」）になる

#### Scenario: 同期で届いた完了済みのリストの完了は conflict にする
- **WHEN** sync.push で、完了済みのリストに買い物の完了の操作が届く
- **THEN** 結果は conflict（reason `already_completed`）で、サーバーの行が返り、リストとカタログの商品は変わらない

#### Scenario: 同期で届いた使えないリストの完了は rejected にする
- **WHEN** sync.push で、ほかのユーザーの個人のリストか、自分が入っていないグループのリストに買い物の完了の操作が届く
- **THEN** 結果は rejected（reason `not_found`）で、リストとカタログの商品は変わらない

#### Scenario: 同期で届いた削除したリストの完了は conflict にする
- **WHEN** sync.push で、論理削除したリストに買い物の完了の操作が届く
- **THEN** 結果は conflict（reason `deleted`）で、リストとカタログの商品は変わらない

#### Scenario: 同期で届いた古い完了は conflict にする
- **WHEN** sync.push で進行中のリストに買い物の完了の操作が届き、リストの状態（状態・完了日時・購入日時・場所）のどれかが操作の時刻より後に書き換えられている
- **THEN** 結果は conflict（reason `stale`）で、リストとカタログの商品は変わらない

#### Scenario: 同期で届いた完了は操作の時刻より新しい購入日時を上書きしない
- **WHEN** sync.push で買い物の完了の操作が届き、チェック済みの商品と同じ名前の未購入のカタログの商品の購入日時が、操作の時刻より後に書き換えられている
- **THEN** その商品は変わらず、ほかの一致した商品は操作の時刻で購入済みになる

### Requirement: チェック 0 件の完了

チェック済みの商品が 0 件のリストで「買い物を完了」すると、システムは確認ダイアログで「リストの商品ごと消す」か「リストだけ消して商品は元に戻す」を選ばせ、選んだ方法でリストを削除しなければならない（MUST）。購入履歴は作らない。サーバーにチェック 0 件のリストの完了が届いたときは、リストを変えずに断る。（ユーザーの決定、2026-11-17）

#### Scenario: チェック 0 件で完了を押すと確認ダイアログを出す
- **WHEN** 商品があり、どれもチェックしていないリストで、完了ボタンを押す
- **THEN** 「リストの商品ごと消す」「リストだけ消して商品は元に戻す」「キャンセル」を選ぶダイアログが出る

#### Scenario: リストの商品ごと消すとリストと同じ名前の未購入の商品を削除する
- **WHEN** チェック 0 件のダイアログで「リストの商品ごと消す」を選ぶ
- **THEN** リストが削除され、リストの商品と同じ名前・同じスコープの未購入のカタログの商品も削除される
- **AND** 同じ名前の購入済みのカタログの商品は残り、購入履歴は作られない

#### Scenario: リストだけ消すとカタログの商品は変えずに買いたいものに戻る
- **WHEN** チェック 0 件のダイアログで「リストだけ消して商品は元に戻す」を選ぶ
- **THEN** リストが削除され、カタログの商品は変わらず、リストにあった商品が「買いたいもの」の一覧に出る
- **AND** 購入履歴は作られない

#### Scenario: キャンセルするとリストはそのまま
- **WHEN** チェック 0 件のダイアログで「キャンセル」を選ぶ
- **THEN** ダイアログが閉じ、リストとカタログの商品は変わらない

#### Scenario: tRPC にチェック 0 件の完了が届くと断る
- **WHEN** チェック済みの商品がない進行中のリストを tRPC で完了しようとする
- **THEN** BAD_REQUEST になり、リストは進行中のまま、カタログの商品も変わらない

#### Scenario: 同期で届いたチェック 0 件の完了は conflict にする
- **WHEN** sync.push で、チェック済みの商品がない進行中のリストに買い物の完了の操作が届く
- **THEN** 結果は conflict（reason `no_checked_items`）で、サーバーの行が返り、リストとカタログの商品は変わらない

#### Scenario: 完了に失敗したら画面にエラーを出す
- **WHEN** 完了ボタンを押し、サーバーが完了を断る（ほかの端末でチェックが外れて 0 件になった場合など）
- **THEN** 画面にエラーのメッセージが出て、リストを読み直し、リストの画面のまま操作を続けられる

### Requirement: リストと同じ名前の未購入の商品も消すリストの削除

リストを削除するときに、リストの商品と同じ名前の商品も消す指定をすると、システムは、1 つのトランザクションで、リストとリストの商品を論理削除し、リストの商品と同じ名前・同じスコープの、未購入で論理削除されていないカタログの商品を論理削除し、その商品のタグの関連を消さなければならない（MUST）。消したリストとカタログの商品は、同期の記録に削除として残す。指定しないときは、今のとおりリストだけを消す。リストの状態（進行中・完了）とチェックの有無は問わない。

#### Scenario: 指定するとリストと同じ名前の未購入の商品を論理削除する
- **WHEN** 「牛乳」「卵」があるリストを、商品も消す指定で tRPC で削除する
- **THEN** リストとリストの商品、同じスコープの未購入の「牛乳」「卵」のカタログの商品が論理削除され、その商品のタグの関連が消える
- **AND** リストとそのカタログの商品の削除が、同期の記録に残る

#### Scenario: ほかのスコープ・購入済み・削除済みの同じ名前の商品は消さない
- **WHEN** 「牛乳」があるグループ A のリストを、商品も消す指定で削除する
- **THEN** グループ B・個人の「牛乳」、グループ A の購入済みの「牛乳」、論理削除済みの「牛乳」は変わらない

#### Scenario: 指定しないとリストだけを消す
- **WHEN** リストを、商品も消す指定をせずに削除する
- **THEN** リストとリストの商品だけが論理削除され、カタログの商品は変わらない

#### Scenario: 使えないリストは商品ごと消せない
- **WHEN** ほかのユーザーの個人のリストか、自分が入っていないグループのリストを、商品も消す指定で tRPC で削除しようとする
- **THEN** FORBIDDEN になり、リストとカタログの商品は変わらない

#### Scenario: 途中で失敗したら何も消さない
- **WHEN** 商品も消す指定の削除で、カタログの商品を消した後、リストの削除に失敗する
- **THEN** カタログの商品もリストも削除の前の状態のまま

#### Scenario: ゲストでは同じ groupId の未購入の商品を消す
- **WHEN** ゲストで、リストを商品も消す指定で削除する
- **THEN** リストとリストの商品、リストの groupId と同じ groupId の、リストの商品と同じ名前の未購入のカタログの商品が、1 つのトランザクションで削除される

#### Scenario: ローカルファーストでは端末の DB で消してキューに削除を積む
- **WHEN** ローカルファーストで、「牛乳」がある送信済みの進行中のリストを、商品も消す指定で削除する
- **THEN** リスト・リストの商品と、リストと同じ groupId の未購入の「牛乳」のカタログの商品が、1 つのトランザクションで消える
- **AND** キューに、カタログの商品の `delete`、リストの商品の `delete`、リストの `delete` が積まれる

### Requirement: ローカルファーストの買い物の完了

ローカルファーストで買い物を完了すると、システムは、サーバーと同じ規則（「チェック済みの商品がある買い物の完了」）で、ユーザー DB のカタログの商品の購入日時・リストから外す商品・リストの状態を 1 つのトランザクションで更新し、キューには複合操作 `finishShopping`（場所だけ）を 1 つだけ積まなければならない（MUST）。カタログの商品の照合は、リストと同じ groupId の、同じ名前の未購入の商品とする（ユーザー DB には自分のスコープの行だけがある）。チェック済みの商品が 0 件なら、ゲストと同じエラー（「購入済みのアイテムがありません」）にし、行もキューも変えない（画面はチェック 0 件で完了を呼ばず、「チェック 0 件の完了」のダイアログを出す）。

#### Scenario: ローカルファーストの完了は端末の DB を更新し複合操作を 1 つ積む
- **WHEN** ローカルファーストで、「牛乳」をチェックし「卵」をチェックせずに、場所を指定してリストを完了する
- **THEN** 同じグループの未購入の「牛乳」のカタログの商品に完了の時刻が購入日時として入り、「卵」のリストの商品は消え、リストは完了になって完了日時・購入日時・場所が入る
- **AND** キューには `finishShopping`（patch は場所だけ）が 1 つだけ積まれ、カタログの商品やリストの商品の操作は積まれない

#### Scenario: ローカルファーストの完了は同じ名前の購入済みの商品の購入日時を変えない
- **WHEN** ローカルファーストで、同じグループに未購入と購入済みの「牛乳」がある状態で、「牛乳」をチェックしてリストを完了する
- **THEN** 未購入の「牛乳」だけが購入済みになり、購入済みの「牛乳」の購入日時は変わらない（サーバーと同じ）

#### Scenario: ローカルファーストではチェック 0 件で完了するとエラーになる
- **WHEN** ローカルファーストで、チェック済みの商品がないリストを端末の DB で完了する
- **THEN** エラー（「購入済みのアイテムがありません」）になり、リスト・リストの商品・カタログの商品・キューは変わらない

#### Scenario: 完了済みのリストは端末の DB でも完了できない
- **WHEN** 端末の DB で、完了済みのリストを完了しようとする
- **THEN** エラー（「このリストは既に完了しています」）になり、行もキューも変わらない
